# Declared batch and flow advisory

Run the companion with Node 22 or newer from the Planner checkout:

```sh
node scripts/assess-process.mjs < tests/fixtures/process/batch.json > batch-advisory.json
node scripts/assess-process.mjs < tests/fixtures/process/flow.json > flow-advisory.json
```

The first example gives a 13-minute declared schedule. The operator works for 7 minutes, the vessel is occupied for 10 minutes and the standalone meter for 3. Measurement overlaps the operator's release of the retained batch. The declared aliquot is 2 mL and the retained state is 10 mL. The meter produces a data identity tied to the delivered aliquot. The data value remains null. The second example gives exactly 120/7 seconds under the ideal once-through model. The ideal value exceeds 17.14 seconds and is at most 17.15 seconds.

## Scope and architecture

Use this command after reviewing a source. Declare the exact operation, material, resource and evidence identities in the versioned input. Compare the resulting timing, occupancy, unresolved requirements and known cost against what the existing workflow needs. Keep the review, applicable configuration evidence, input and output together. This CLI does not transform a Labstep or Portal record automatically, look up provider access, or replace either source of truth.

This prototype adds a batch scheduler and a separate ideal-flow evaluator behind one explicit CLI. It reuses the repository's strict original-byte JSON and exact rational arithmetic. The existing liquid-handler and reviewed-ledger evaluators retain their own scope. A general engine rewrite would have to reproduce those independently tested behaviours and invent interfaces for unsupported hybrid processes. Separate profiles let the new cases show which additional semantics are useful before any production integration.

## Input and result contract

The closed root is `{schema, binding, sources, costs, process}`. Use `lab-automation-planner/process-advisory-input/1`. The binding has `case_id`, `revision` and a matching `evidence` source ID. Sources are `{id, kind, version, url}` where `declared_case` has a null URL and `public_role` has a stable HTTPS locator. Each resource binds an ID, a kind, an exact configuration ID and revision, availability and declaration evidence. The same configuration's capacity and positions must jointly fit. A fit from an alternative or another revision does not clear the selected resource.

Batch inputs supply a declared batch, resources, operations, joint fit and control. Operations have ID, kind, predecessors, duration in minutes, exclusive resource IDs, a kind-specific payload and declaration evidence. The checked-in example supplies all fields for load, hold, sample, handoff, standalone measure and retained release. A generic `task` uses an operator or provider and a null payload. An `observe` uses a distinct observer and a payload with `batch_state_id`, `data_id`, `during_id` (the hold), `offset_min` from that hold's start, and declaration `evidence`. It occupies the observer during the hold and leaves material unchanged. The sample operation splits one exact state into retained and aliquot identities. Handoff moves the aliquot to a distinct delivered state whose location must match the standalone meter. Measurement reads that identity without assuming consumption.

The batch profile uses stable list scheduling with exclusive resources, explicit predecessors and exact fixed offsets for in-situ observation. It allows unrelated operations to overlap and does not prove a global optimum. An anchored observation that conflicts with the computed resource order stays unresolved. The prototype does not reorder earlier activities to resolve it. The timeline is relative to the declared case and says nothing about a booking. Incomplete cases retain labelled, counterfactual material projections and known work subtotals. They withhold a complete elapsed or labour total and any scheduled data placeholder that depends on an unresolved operation. Unknown or data-dependent control withholds the full timeline and material outcomes. A `data` row always carries a null value.

Flow inputs declare hold-up volume, volumetric rate, feed/stream/inlet/outlet/collection identities, optional in-line observation and thresholds. V1 supports volume in `uL` or `mL`, flow in `uL/min` or `mL/min`, and threshold seconds. It returns exact ideal residence only for the declared once-through steady-state model. Missing routing, an unresolved observation binding, missing rate, incompatible units, recirculation or result-dependent control stays incomplete or unsupported. Actual hydraulic fit, throughput, startup, shutdown and elapsed time remain unresolved.

The cost object contains one currency and a list of declared necessary cost components. Null amounts are unknown. The report exposes the known subtotal, missing component IDs and complete total only when every amount is present. No profile ranks a result or creates a quote. The output uses `lab-automation-planner/process-advisory/1`, a release ID, the SHA-256 digest of canonical input, and source/configuration IDs with their evidence revisions. Decimal strings and reduced rational objects are exact. Null denotes an unavailable value. The CLI takes no arguments, reads at most 128 KiB of UTF-8 JSON and emits one JSON record to stdout. Exit 0 can include an incomplete advisory result. Exit 2 emits a structured refusal without echoing supplied prose, IDs or values.

## Regression, failures and rollback

The independent case file is retained unchanged in `tests/fixtures/process/independent-oracle.json`. `node --test tests/process-advisory.test.js` exercises the actual command, required numeric witnesses, wrong material lineage, concurrent and exclusive occupancy, incomplete or contradictory fit and cost, missing timings, routing and unsupported control. It verifies the reviewed v1 result against the previous release's exact synthetic bytes and checks that each command refuses the other's input format.

The production build, UI, HTTP endpoints, profiles and exporters do not consume this profile. To roll back, stop invoking the command and return to the existing Decide or reviewed assessment path. There is no state or schema migration to undo. Retain existing inputs and reports with their release. A future process input version should require an explicit conversion with a loss report. Keep this profile opt-in until resource scheduling, facility compatibility evidence and required process semantics are independently validated on additional cases.
